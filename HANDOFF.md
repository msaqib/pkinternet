## 1. Who, what, why

RIPE Atlas measurement study of Pakistan's internet routing. Author: Rayan Atif, LUMS,
supervised by Dr. Saqib Ilyas, funded by the APNIC Foundation. Core question: how
effectively is Pakistan's Internet Exchange Point (PKIX, plus a second exchange PIE) being
used, and if it isn't, what does that cost users. The flagship deliverable is a 7-day,
all-connected-probe measurement panel (Exp 07) targeting a stratified sample of Pakistani
websites, feeding a paper submission (ACM/AINTEC '26).

**Read `CLAUDE.md` (repo root) first**, it's the standing project reference: experiment
inventory, key ASNs, known measurement artifacts, RIPE Atlas quirks, findings-so-far. This

## 3. The central methodological story: the trombone detector overhaul

This is the thing that touches nearly every number in the paper, understand it before
touching any Results-section number.

**The old detector** (what `running_draft.tex`'s *comments* still preserve, and what
produced the 15.1%-headline generation of numbers) allowed a trace to be classified
"tromboned" two ways: a confirmed foreign hop, **or** RTT alone (a ≥60ms jump between
consecutive hops, or any hop ≥70ms, with no foreign hop required). Dr. Saqib's review
comment identified the RTT-alone path as insufficient evidence, domestic congestion can
produce the same RTT signature as a genuine foreign detour, so it can't be trusted to
distinguish the two.

**The final detector** (5-condition AND, no independent RTT-only trigger), a trace is
tromboned iff at least one responding hop satisfies **all** of:
1. Resolves to a real country code that is not `PK`.
2. Is not a private/internal IP.
3. Its ASN is not on the artifact-exclusion list: **`{6327 (Shaw), 174 (Cogent)}`**.
4. It actually responded (a timeout hop is skipped, never counted as foreign).
5. Its own RTT is between **40ms and 500ms**.

**Why Shaw and Cogent are excluded:** both are foreign-registered ASNs (Shaw=Canada,
Cogent=US) whose specific hops are confirmed, by RTT and in Shaw's case a matching PTR
record, to be physically inside Pakistan. Without excluding them, a domestic hop gets
misread as a foreign exit. **Cogent was the single biggest correction found this session**:
adding it to the exclusion list (it was previously *not* excluded, only Shaw was) dropped
the headline trombone rate from 7.50% to 5.52%, and explains why the exit-country
attribution's "United States" count fell from 1,750 (old) to 253 (final), those extra 1,497
"US" exits were Cogent's Pakistan-based router misread as foreign, not real detours.

**The 40ms/500ms thresholds are not distance calculations.** This was a specific,
repeated point of confusion this session (Dr. Saqib asked directly "what landing point would
that be? France? Singapore?"). They are **empirically calibrated** from the observed ceiling
of purely domestic Pakistani RTT (tops out ~40ms in the data) cross-checked against known
foreign hop ranges (Singapore 60-90ms, Europe 100-130ms). No specific city's geodesic
distance produced these numbers. The paper's *current* live Tromboning Classification text
(before the corrections doc's fix) wrongly implies a distance-based derivation ("physical
round-trip to the nearest international exchange"), that phrasing is incorrect and the
correction removes it.

**A 20ms-floor sensitivity test was run and rejected.** Sameera raised whether 40ms was too
conservative (a genuinely close foreign destination, e.g. Oman/UAE, might answer under 40ms
and get wrongly excluded). Tested directly: lowering to 20ms never surfaced a genuine
nearby-foreign hop, no Oman, no Gulf country ever appeared. It only surfaced more
registration-artifact hops (first Cogent, then a Cloudflare edge on `trax.pk`/`sonic.pk`).
**Recommendation, already acted on: keep 40ms**, fix the artifact list instead of loosening
the floor. A further recommendation (generalizing `ARTIFACT_ASN` to reuse the project's
existing `CDN_KEYWORDS` list from `site_collection/classify_pk_hosting.py`, so future
Cloudflare/Akamai/Fastly-style cases are pre-empted rather than discovered one at a time) is
written up but **not implemented in the production code**, only in this session's standalone
scripts.

**This detector is NOT yet in the production pipeline.** `census_sweep.py` (Exp 4.1) and
`tromboning_sweep.py` (Exp 04), which `panel_monitor.py` imports and calls live for the whole
Exp 07 panel, still have `ARTIFACT_ASN = {"6327"}` (Shaw only) and still have the OR-based
RTT-alone backstop path. Every "final" number in this handoff and in the corrections doc
comes from a **separate reprocessing of the raw archive**, not from re-running the live
pipeline. If you want the production code itself fixed (not just the paper's numbers), that's
a distinct, not-yet-done task: edit `ARTIFACT_ASN` and remove the OR-branch in both files.

**5.52% is a lower bound, not a point estimate (Sameera's comment, verified this session).**
65.2% of Pakistani-class traces (49,285/75,600) have a hop that never responds before the
last hop we can classify, the detector can only under-count from this, never over-count. A
targeted robustness check, reclassify a gapped trace as tromboned only if its destination RTT
matches the 5th-95th percentile of other, fully-visible confirmed rounds to the *same* site,
raises the rate to **8.3%** (script: `evidence_supported_trombone.py`, same directory as the
other final-detector scripts). Only applies to the 8 sites with a confirmed round to
corroborate against; cannot move the other 29. Written up as a named robustness bound in the
corrections doc (RQ1 section), not folded into the 5.52% headline, it reintroduces RTT as
evidence and is a weaker standard than the confirmed-hop rule elsewhere in the paper. First
attempt at this used the full min-max RTT range per site instead of a percentile band and
got 9.7%, wrong: a handful of "confirmed trombone" rounds have a ~1ms destination RTT, a
Paris-traceroute multipath artifact, not a real fast foreign round, letting it into the
matching window over-reclassified. Watch for this if you touch that script.

**Not recomputed, flagged as out of scope or unverified rather than silently left stale:**
PKIX/PIE zero-crossing scan and the "11,756 detours" figure (broader, all-classes scan, not
just the 75,600 Pakistani-class population this session's detector work covers), "23 pairs
handed to both PTCL and Transworld," the per-site "state agricultural bank at 86%" and
"federal housing authority at 89%" figures, the RQ2 "as a secondary check, three-day
snapshot" 2.9×→1.9× last-mile adjustment. The Abstract's "55%" Financial Services figure was
separately checked against a verified 58.3% and never reconciled, still an open discrepancy.

These are not new this session but come up constantly and are easy to get backwards:

- **Two probes are excluded from the general 14-probe analysis set** (16 returned data, 14

  duplicate of probe 7613, same ISP, same city, ~5km apart) and **7764** (PTCL, Lahore/LUMS
  anchor, 90% packet loss throughout the run). These two are **distinct** from the two
  data-quality-flagged-but-retained probes below, easy to conflate, Dr. Saqib asked about
  this confusion directly in review comments.
- **1016393** (PTCL, Mianwali) — retained, not one of the two exclusions above, but flagged:
  full cadence for ~29 hours, then only 7.8% of expected traceroute rows for the remaining

  in §2 above.
- **62224** (Transworld, Lahore) — retained for ping/RTT purposes only. Every one of its
  16,799 traceroute rows has `hop_count = NaN` (not even the usual "255" timeout marker),
  its path is structurally invisible due to aggressive ICMP filtering, but 77% of its ping
  rounds return a valid RTT, so it's kept for every RTT-based result and excluded only from
  hop-count/path-based ones.
- **The 98-vs-100-site correction**: `toptop.net` and `youth.cn` were dropped from the
  sample (not relabelled, fully dropped) after being traced to a reseller-attribution
  mislabeling (their real host, Meteverse Limited, is reached via a direct BGP-peering
  relationship with Gerry's/S.B Link Network, confirmed via RIPEstat `asn-neighbours`, not a
  migration). **Important**: since both sites were *already* classified "Abroad" (not
  "Pakistan") under the corrected classification regardless of whether they're dropped or
  kept, the drop does not change the 75,600-trace Pakistani-class denominator used
  throughout RQ1-3. It *does* change any total that sums across all three classes: raw
  traces 222,944→218,480, raw pings 445,749→436,828, cleaned traces 204,384→200,292, cleaned
  pings 313,276→305,116. The Abstract already uses the corrected numbers; Data Cleaning
  (line ~611 as of last read) and the Conclusion (line ~942) still don't, that's part of the
  still-pending corrections in §6/§14 of the corrections doc.
- **Site classification is NOT purely ASN/country-based for every site.** Design-time
  classification (Pakistani/CDN/Abroad) is Team-Cymru-ASN-based. A *separate* correction
  step (`geo.py`'s `cmd_correct()`) can move a site from Pakistani to Abroad using **RTT
  alone** (nearest probe >20ms, no ASN or hop corroboration required in the live code). This

  do not classify a site as abroad based on a high RTT... right?", answer: yes, it still
  does, for exactly 3 sites, `phf.gop.pk` (206ms), `toptop.net` (99ms), `youth.cn` (77ms)). A

  directory) and confirms the same 3 sites, but **has not been merged into `geo.py`**, the
  code that actually produces the paper's numbers is still the RTT-only version.

## 8. The Introduction's "37%" figure, and what backs it (or doesn't, yet)

`running_draft.tex`'s Introduction currently states: "Nearly 37% of the 0.2M most popular
domains in Pakistan are either hosted by local network operators or by international CDN
operators that also have local caches in Pakistani ISP networks." **This number comes from a
completely separate, standalone analysis done this session** (classify the top ~200,000
globally-ranked Tranco domains, not the paper's own `.pk`-filtered 1,814-site candidate
pool; check each site's hosting ASN; for CDN ASNs, additionally require a confirmed RIPEstat
`asn-neighbours` peering relationship with a Pakistani ASN before counting it as
"locally-cacheable"). Final number: 36.98%, rounds to 37%.

**This methodology is not documented anywhere in the paper's actual Methodology section.**
Site Selection (§subsec:sites) only describes the `.pk`-filtered pipeline that produced the
1,814-site pool feeding the 98-site sample; a reader has no way to trace where "37%" comes
from. If this number stays in the Introduction, **a new methodology subsection describing
this Tranco-200k + RIPEstat-peering pipeline needs to be written**, this has not been done.
The alternative discussed but not chosen: use the paper's own 1,814-site pool composition
instead (72%, no new methodology needed since it reuses the existing Site Selection
pipeline, but is a different, `.pk`-domain-biased question, not a clean substitute).

Scripts and intermediate CSVs for the Tranco-200k/RIPEstat work were **not copied into the
repo**, they exist only in this session's ephemeral scratchpad (a temp directory tied to
this specific Claude session) and are **not accessible to a new agent or session**. If this
work needs to be reproduced, it needs to be rebuilt from scratch: classify domains from
`data/tranco_ZJJYG.csv` (full Tranco top-1M list already in the repo) using the same
country/CDN-keyword method as `site_collection/classify_pk_hosting.py`, then check each
resulting CDN ASN against RIPEstat's `asn-neighbours` endpoint for a Pakistani-ASN peer,
resolved via Team Cymru bulk WHOIS (`AS<number>` query format returns country + org name
directly, confirmed this session, no need for a separate IP lookup step).
